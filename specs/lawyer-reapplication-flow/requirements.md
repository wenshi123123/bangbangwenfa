# 律师入驻驳回后的重新申请流程需求

## 1. 背景与现状

当前页面 `/lawyer/pay?applicationId=8` 显示“该入驻申请未通过”。这是符合旧申请状态的展示：该申请已经被审核拒绝，不能继续付款。

真正的堵塞出现在重新申请链路：创建申请接口目前会查询用户最近的一条 `lawyer_applications` 记录，并在记录存在时直接返回旧申请 ID，没有区分 `pending`、`rejected`、`approved` 等状态。因此，用户点击“重新申请入驻”并提交资料后，可能仍被返回旧的已拒绝申请，页面再次显示 `applicationId=8`，看起来就像重新提交没有生效。

## 2. 目标

让律师在申请被拒绝后可以：

1. 看到明确的拒绝原因；
2. 一键进入重新申请，并复用可复用资料；
3. 只修改需要修正的内容后提交；
4. 生成一条全新的申请记录和新的申请 ID；
5. 继续进入正确的审核/付款流程；
6. 保留旧申请的审核历史，避免账务和审核记录混乱。

## 3. 用户故事

### 3.1 被拒绝的律师

作为一名申请被拒绝的律师，我希望看到具体审核意见，并可以从原申请直接重新提交修正后的资料，而不必从零开始填写。

### 3.2 管理员

作为管理员，我希望每次重新申请都是独立、可追溯的记录，并能看到它来自哪一次被拒绝的申请。

### 3.3 财务/运营

作为运营人员，我希望拒绝申请不会生成可付款订单，重新申请只有在新记录创建成功后才进入付款，避免重复扣款、错账或旧申请被付款。

## 4. 业务规则

1. `rejected` 申请不可付款、不可原地改成 `pending`。
2. 重新申请必须创建新申请记录，旧申请只读保留。
3. 新申请的 `review_status` 必须为 `pending`，`payment_status` 必须为 `pending`。
4. 新申请的价格、套餐和支付状态必须由服务端重新计算，不能信任前端传入的金额。
5. 同一用户可以有多条历史申请，但同一时间最多允许一条待审核申请；若已有待审核申请，应引导用户查看该申请，而不是重复创建。
6. 已通过并完成付款的申请不得通过“重新申请”重复入驻；若要变更资料，应走独立的资料变更流程。
7. 免费体验申请继续使用现有“免费体验申请”路径，不与付费申请混用，也不通过修改旧申请实现。
8. 重新申请必须校验当前登录用户对原申请的所有权，不能仅相信 URL 中的 `applicationId`。

## 5. 功能需求（EARS）

### R1：拒绝页

- 当当前用户打开一条属于自己的 `rejected` 申请时，系统应显示拒绝原因、申请编号和“重新申请入驻”按钮。
- 当用户打开不属于自己的申请 ID 时，系统应返回无权访问，不泄露申请资料和审核意见。

### R2：预填重新申请

- 当用户点击“重新申请入驻”时，系统应打开入驻向导，并在完成身份校验后预填原申请中允许复用的资料。
- 系统应在向导顶部展示原审核意见，并标注需要重点修正的字段。
- 用户仍应可以修改所有可编辑字段，并重新上传需要更新的材料。

### R3：创建新申请

- 当用户完成重新申请并提交时，系统应先检查该用户是否已有待审核申请。
- 若没有待审核申请，系统应创建新的申请 ID，不得返回旧的 rejected 申请 ID。
- 新记录应保存来源申请 ID、修订次数和本次提交时间；旧记录不得被覆盖。
- 创建成功后，系统应把用户重定向到新申请 ID 对应的付款/审核页面。

### R4：重复提交保护

- 当用户连续点击提交或网络重试时，系统应避免创建重复申请，并返回同一个本次提交结果。
- 提交按钮在请求处理中应禁用，并在失败时给出可理解的错误和重试入口。

### R5：付款与审核衔接

- 当付款页收到 rejected 申请 ID 时，系统应继续显示“不可付款，请重新申请”，不得显示“暂无可支付申请”这种模糊信息。
- 当付款页收到新建的 pending 申请 ID 时，系统应显示对应套餐、金额和下一步操作。
- 只有新申请审核通过且满足现有付款规则时，才允许进入可付款状态。

### R6：后台可追溯性

- 管理后台应显示“第几次申请”和“来源申请编号”。
- 管理员审核新申请时，应能查看上一条拒绝原因，但不能误把旧申请改成新申请。

## 6. 数据需求

建议在 `lawyer_applications` 增加以下字段：

- `resubmitted_from_id`：来源申请 ID，可为空；
- `revision_no`：第几次申请，首次为 1；
- 如现有 `review_remark` 已能保存审核意见，则继续复用，不重复新增字段。

迁移要求：

- 现有历史数据不修改；
- 现有申请的 `revision_no` 默认回填为 1；
- 新字段建立索引，便于按用户和来源申请查询；
- 部署前先在测试数据库验证，部署后检查旧申请、正在审核申请和重新申请三类数据。

## 7. 非目标

- 不改变管理员审核权限模型；
- 不自动把被拒绝申请改为通过；
- 不自动免除付费；
- 不改变免费体验的审核规则；
- 不删除历史申请或历史订单。

## 8. 验收标准

1. 用一个曾被拒绝的律师账号点击“重新申请入驻”，页面能预填资料并显示拒绝原因。
2. 提交后数据库出现新的申请 ID，旧申请 ID 保持 `rejected` 不变。
3. 提交成功后的 URL 使用新的申请 ID，而不是旧的 `applicationId=8`。
4. 新申请可以正常进入审核/付款页面；旧申请不能付款。
5. 重复点击提交不会产生两条相同的新申请。
6. 管理后台能区分旧申请和新申请，并显示来源关系。
7. 普通新申请、免费体验申请、已通过律师三种路径均不回归。

## 9. 当前结论

这不是单纯要求用户“再走一遍流程”，而是当前重复申请判定过于粗糙导致的流程堵塞。推荐采用“保留旧记录 + 新建修订申请 + 自动预填”的方案：审核历史完整，账务边界清晰，用户也不需要从头填写。
