# 律师入驻支付与体验审核需求

## 1. 文档目的

解决律师提交入驻资料后进入支付页却显示“暂无可支付申请”的问题，并补齐“特定律师可申请免费体验”的受控入口。

本版需求对应已确认的简化方案；本次仅修改本地代码与文档，不修改线上数据、不提交部署。

## 2. 当前问题

### 2.1 支付页问题

律师完成资料和套餐选择后，页面跳转到类似：

`/lawyer/pay?applicationId=8`

但页面显示“暂无可支付申请”。当前实现存在两个风险：

1. 创建申请时主要依赖浏览器 `localStorage` 中的 `user_info` 保存用户归属；该信息为空、过期或与当前登录账号不一致时，申请会保存到错误的 `user_id`。
2. 支付页虽然带有 `applicationId`，但后端为了防止越权没有使用该编号，而是只查询当前登录账号的申请。因此申请记录与当前账号归属不一致时，就会被判定为“没有可支付申请”。

这不是支付渠道本身的报错，也不是整站部署失败；支付订单创建请求尚未执行。

### 2.2 免费体验入口问题

当前系统已经有后台“赠送体验开通”功能，但律师在前台申请入驻时没有“申请免费体验”入口。律师只能先走支付流程，再由管理员后台特批。

这属于产品流程缺口，不建议让所有律师直接免付款开通，否则会造成付款统计、审核权限和体验资格滥用问题。

## 3. 产品目标

1. 正常付费律师能够稳定完成“提交资料 → 支付 → 等待审核”。
2. 特定律师能够通过受控流程申请免费体验，不需要真实付款，但必须经过身份和条件校验。
3. 普通付费审核与免费体验审核在状态、订单、会员期限和统计中明确区分。
4. 不允许通过修改 URL 中的申请编号访问或支付其他账号的申请。
5. 历史申请和历史订单不被删除、不被无故改价。

## 4. 用户流程

### 4.1 正常付费入驻

1. 律师登录账号。
2. 填写入驻资料并选择套餐。
3. 服务端从登录 Token 获取账号 ID，创建申请并绑定当前账号。
4. 支付页根据“申请编号 + 当前账号归属”查询申请。
5. 申请存在、未支付、未拒绝且价格大于 0 时，显示套餐金额和“确认并支付”。
6. 支付成功后，申请变为“已支付/待审核”；支付回调不得直接批准律师。
7. 管理员确认资料后，才可执行普通“批准入驻”。

### 4.2 受控免费体验

1. 律师填写资料并选择“申请免费体验”。
2. 系统显示说明：免费体验不是正式付费入驻，需要后台审核。
3. 律师填写体验理由，提交后等待后台审核。
4. 系统创建一条待审核申请，金额为 0，但不把它标记为已付款。
5. 管理员在申请详情中看到“赠送体验开通”。
6. 管理员必须填写原因和有效期（1～365 天），点击确认后开通体验。
7. 服务端校验管理员权限，校验通过后：
   - 申请审核状态为已通过；
   - 会员状态为 `trial`；
   - 生成金额 ¥0.00 的体验订单；
   - 生成体验会员记录并写入到期时间；
   - 记录管理员、原因和审核时间；
   - 不修改为真实付款，不生成微信支付订单。

## 5. 功能需求（EARS）

### R1. 账号归属

- 当已登录用户提交入驻申请时，系统必须从服务端验证的登录 Token 获取用户 ID。
- 系统不得把浏览器提交的 `userId`、`x-user-info` 或 URL 参数作为最终授权依据。
- 当请求未登录或 Token 无效时，系统必须拒绝创建申请并返回明确的登录提示。

### R2. 支付申请查询

- 当用户打开支付页时，系统必须校验申请编号属于当前登录账号。
- 当申请属于其他账号时，系统必须返回无权访问，不得显示金额或创建订单。
- 当申请属于当前账号且未支付、未拒绝、价格有效时，系统必须显示可支付页面。
- 当申请不存在、已支付、已拒绝或价格无效时，系统必须显示对应状态，而不能笼统显示“暂无可支付申请”。

### R3. 正常支付

- 当用户点击“确认并支付”时，系统必须使用服务端保存的套餐价格，不信任浏览器金额。
- 当支付订单创建失败时，系统必须展示具体失败原因，并允许重新尝试。
- 当支付成功时，系统必须只更新支付状态，不得自动绕过管理员审核。

### R4. 免费体验申请

- 当用户选择“申请免费体验”时，系统必须明确提示该申请需要管理员审核。
- 当用户未填写必要资料时，系统不得创建体验申请。
- 当体验申请创建成功时，系统必须显示“已提交体验申请，等待审核”，不得跳转到真实支付页。
- 体验申请必须与当前登录账号绑定。

### R5. 免费体验审核

- 当管理员执行普通批准且申请未支付时，系统必须拒绝该操作。
- 当管理员执行赠送体验时，系统必须要求原因和 1～365 天的有效期，并弹出二次确认。
- 当体验天数非法或原因为空时，系统必须拒绝开通。
- 当赠送体验成功时，系统必须生成可审计的零金额体验订单，并记录原因、管理员和有效期。

### R6. 订单和统计

- 用户订单列表必须区分普通律师入驻订单和赠送体验订单。
- 管理后台订单列表必须能按“赠送体验”筛选。
- 赠送体验订单金额必须为 ¥0.00，不能计入实际收入、支付成功率或退款金额。
- 普通付费订单和赠送体验订单必须保留独立状态，不能互相覆盖。

## 6. 数据与安全边界

- 不删除历史申请、历史支付订单和历史会员记录。
- 申请归属修复只能在确认手机号、当前登录账号和申请资料一致后执行。
- 不允许仅凭 `applicationId` 修改申请归属或发起支付。
- 免费体验不新增环境变量；权限由管理员登录态控制，原因和期限写入审计记录。
- 体验资格必须有明确到期时间，不能永久有效。

## 7. 验收标准

### 正常付费场景

- 新账号提交资料后，支付页能显示正确套餐和金额。
- 刷新支付页后仍能找到同一申请。
- 使用其他账号打开同一个申请编号时，不能看到金额，也不能创建支付订单。
- 支付成功后显示“已支付，等待审核”，后台仍需人工批准。

### 免费体验场景

- 律师可在入驻流程中看到“申请免费体验”。
- 体验申请不会跳转真实支付，也不会创建微信支付订单。
- 管理员输入原因和期限并确认后，可以开通体验。
- 用户和后台都能看到一笔 ¥0.00 的赠送体验记录。
- 体验到期后，律师不能继续以体验状态接单。
- 普通审核按钮不能批准未付款申请。

### 异常场景

- 清空或伪造浏览器 `user_info` 后，不能把申请挂到错误账号。
- 缺少生产数据库迁移时，体验审核必须给出明确配置错误，而不是静默成功。

## 8. 分阶段实施建议

### 第一阶段：修复本次支付故障

- 服务端统一解析登录身份。
- 修复申请创建时的账号绑定。
- 支付页增加申请归属校验和区分状态提示。
- 核对并修复现有申请 8 的账号归属。

### 第二阶段：补齐前台体验申请

- 在套餐选择步骤增加“正常付费入驻”和“申请免费体验”两个明确选项。
- 免费体验选项只创建待审核申请，不调用支付接口。
- 增加体验申请状态提示。

### 第三阶段：生产验收

- 确认数据库迁移已执行。
- 确认后台管理员权限和体验审核接口可用。
- 用普通账号测试付费流程。
- 用受控账号测试免费体验流程。
- 检查用户订单、后台订单、会员到期时间和审计记录。

## 9. 本次不做的事情

- 不开放所有律师无条件免费入驻。
- 不通过 URL 参数绕过账号归属校验。
- 不把免费体验伪装成已付款订单。
- 不修改现有套餐价格。
- 不删除或重建线上历史数据。
