# 免费律师体验与入驻状态闭环需求

## 1. 问题概述

免费体验申请目前可以被管理员审核通过，数据库中的律师资格和零金额体验订单也可能已经创建，但用户界面没有稳定地把“审核中、已开通、已拒绝”展示出来。生产环境实测还发现，审核通过通知使用了生产 `notifications` 表不存在的字段，导致通知没有写入。

同时，申请接口虽然会拦截重复申请，但对前端返回的是“成功并带原申请编号”，页面仍会跳到支付页，用户容易误以为可以再次申请或需要付款。

## 2. 目标

1. 免费申请提交后，用户能明确看到“审核中”，并在“我的订单”中看到该申请。
2. 管理员通过免费体验后，用户能看到“体验已开通”、有效期、律师身份入口和零元体验订单。
3. 申请审核中的用户不能创建第二条申请，也不能被引导到付款流程。
4. 被拒绝的申请仍可修改资料后重新提交；已通过或已开通体验的用户不能重复入驻。
5. 审核流程不能出现“申请已通过但律师/会员/订单只创建了一部分”的半成功状态。

## 3. 用户故事

- 作为申请免费体验的律师，我希望提交后能看到审核中状态，而不是回到普通付款页面。
- 作为审核通过的律师，我希望登录后立即看到体验资格、到期时间、律师工作台入口和一笔零元订单。
- 作为审核中的律师，我希望再次点击入驻时得到明确提示，而不是生成重复申请或重复支付。
- 作为管理员，我希望审核通过操作要么完整成功，要么明确失败并可重试，不留下半成品数据。

## 4. 验收标准（EARS）

### 4.1 申请状态

- 当用户提交免费体验申请时，系统应创建一条 `review_status=pending`、`approval_mode=complimentary_requested` 的申请，并在提交结果中返回申请编号和审核中状态。
- 当用户存在任意 `review_status=pending` 的申请时，系统应拒绝创建新申请，返回结构化状态 `APPLICATION_PENDING`、原申请编号和申请类型；前端应跳转到申请状态页或展示审核中卡片。
- 当用户存在已审核通过的付费或免费申请，或存在有效律师身份时，系统应拒绝再次入驻，并提供进入律师工作台的入口。
- 当申请为 `rejected` 时，系统应允许用户通过新 revision 重新提交，旧申请保持只读。

### 4.2 免费体验审核

- 当管理员以免费体验方式审核通过时，系统应一次性完成：申请状态、律师身份、会员资格、零金额体验订单和用户通知。
- 当上述任一写入失败时，系统不得向用户呈现“已通过”而只完成部分数据；操作应可安全重试且不会产生重复会员或重复体验订单。
- 免费体验不得把 `payment_status` 伪装成 `paid`，但用户界面必须显示为“已开通/体验中”，而不是“待付款”。

### 4.3 用户可见反馈

- 当免费申请处于审核中时，“我的订单”应显示“免费体验申请（审核中）”，金额为 0 元，并显示申请时间。
- 当免费体验已开通时，“我的订单”应显示“律师赠送体验开通”、金额 0 元、状态“体验中/已完成”和到期时间。
- 当免费体验已开通时，用户中心和律师入口应显示“律师身份已开通”，并可进入律师工作台。
- 当审核通过通知创建失败时，不得影响核心资格开通；系统应记录可追踪的服务端错误，并允许用户通过用户中心状态查询看到结果。

### 4.4 已确认的产品规则

- 免费体验审核通过后，系统必须向用户消息中心发送“体验资格已开通”通知；通知中应包含开通结果、体验期限和进入律师工作台的入口。
- 用户中心、申请状态页和消息中心应根据实际审核结果显示“审核中、已通过、已拒绝、已过期”等状态，不以 `payment_status` 单独推断免费体验状态。
- 免费体验审核通过后，用户可以直接在律师中心的“续费”页面购买正式套餐；续费不重新走律师资料提交和管理员审核流程。
- 免费体验期间再次点击律师入驻时，页面应提示已有律师身份/体验资格，并提供“进入律师工作台”和“续费”入口，不创建新的入驻申请。
- 审核中的申请再次提交时，页面应提示“您已有申请正在审核中，请勿重复提交”，并提供“查看申请状态”按钮。
- 免费体验订单必须显示订单编号、0 元金额、开通时间、到期时间、体验理由/审核理由和当前状态。

### 4.4 安全与一致性

- 所有申请状态查询和订单查询必须以当前登录用户身份为准，不能信任 URL 中任意 `userId` 作为授权依据。
- 体验订单以 `application_id` 唯一，审核接口重复请求不得创建第二笔体验订单或第二套同源会员记录。
- 通知写入只能使用生产表实际存在的字段；关联申请编号应放入现有 `data` JSON，不得写入不存在的列。

## 5. 状态流转

```text
提交免费申请
  -> complimentary_requested / pending
  -> 管理员通过
       -> complimentary / approved / trial
       -> 消息中心通知
       -> 生成 0 元体验订单
       -> 可进入律师工作台
       -> 可从“续费”直接购买正式套餐
  -> 管理员拒绝
       -> rejected
       -> 修改资料后重新申请
```

付费续费路径为：

```text
体验中或正式会员
  -> 律师中心 / 续费
  -> 选择套餐并支付
  -> 更新会员期限
```

续费不创建新的 `lawyer_application`，也不触发入驻审核。

## 6. 范围与非目标

### 范围

- 律师免费体验申请、付费申请的状态机和重复申请拦截。
- 管理员免费审核的完整性和幂等性。
- 用户中心、申请支付页/状态页、通知和订单展示。
- 必要的数据库唯一约束或事务/RPC。

### 非目标

- 不改变现有套餐价格、支付金额和微信支付流程。
- 不改变审核员权限模型和免费体验审核理由/有效期规则。
- 不删除历史申请、历史订单或历史审核记录。

## 7. 当前证据

- 生产申请 `id=11` 已是 `approved + complimentary`，对应律师为 `active/trial`，会员记录为 `trial`，零元体验订单已存在，说明核心开通写入路径能成功。
- 生产 `notifications` 表字段为 `id,user_id,type,title,content,data,is_read,created_at,read_at`，没有 `related_id`；当前审核代码写入 `related_id`，因此审核通过通知会失败。
- `user/orders` 当前跳过 `approval_mode=complimentary` 的申请记录；审核中免费申请没有对应零元订单，因此会在“我的订单”中消失。
- `payment-context` 有 `complimentary_pending`，但没有 `complimentary_active` 分支；审核通过的免费申请可能落入普通待支付逻辑。
- 申请接口对重复申请返回 HTTP 成功并带旧申请编号，前端统一跳转到 `/lawyer/pay`，状态语义不够明确。
